## 原因和证据

单店重置过滤指定店铺的业务记录，其他店铺的数组位置自然前移。旧 diff 比较 position 后发送整条 row，造成大量正文被重复上传。生产失败停在 stage_workbench_rows，错误 54000，已暂存 8,379,761 字节，回执 result_revision 为 null，账号 revision 仍为 1；没有执行提交。保留该未完成暂存批次。

用户已导出最新重置后草稿，另存并校验 SHA-256。该草稿与原有 resetStoreBusiness 的输出逐字段相同，不含额外修改。私有原文不提交 GitHub。

- 候选 SQL `supabase/proposals/20261023092148_compact_workbench_positions.sql`：同一事务替换 stage/commit 两函数，严格区分紧凑操作与 row 操作。提交时在原账号 head 锁及 revision CAS 内检查目标存在，仅更新 position。旧正文/删除操作继续兼容。
- 8 MiB、100000 操作、单块限制、认证、RLS、幂等回执、本机备份均保留。没有更改经营计算、resetStoreBusiness、数组顺序、页面、导入、旧 JSONB 或超时上限。

## 失败与回退

- 安装事务失败：全部 DDL 回滚，前端保持现状，草稿保留。
- 安装成功但部署失败：新函数兼容旧 payload，保持其运行，不提交重置；旧前端超限仍安全保留草稿。
- 新前端异常：可回到上一个 **rows-v1** 前端构建，同时保留新函数；未确认请求、全部回执、暂存和草稿保留。不能回退到旧 JSONB 模式。
- **不得直接恢复旧 commit 函数**：它会忽略未完成的紧凑操作。若确需函数降级，须另行批准，停写并保留全部状态，确认没有任何未完成紧凑批次/在途写入后才可事务恢复。否则采用前向修复或保留兼容函数。
- 重置已提交后不能用旧 JSONB 或旧全量快照覆盖。需要撤销时，先导出最新云端和设备草稿，核对切换后新增数据，通过现有单店备份恢复校验另行批准；店铺已有替换数据时必须停止。

本报告不代表生产恢复验收通过。真实生产重置提交、刷新读取和跨设备一致性仍须在批准启用后分别验证。
