# 报表导入单条记录超过前端分块目标

状态：本地修复、286 项回归和 rows-v1 生产构建通过，尚未发布本次修复。没有生产写入、迁移或配置调整。

## 确认的故障

正式站及 GitHub main 均为 `6af496b7ee868d3a878a620d9e3193d5741b02dc`，正式构建为 rows-v1。本次使用该提交的父树及合并提交的两个权威文件恢复独立源码，未取根目录历史修改。

报表导入后的未同步备份已另存，SHA-256 为 `8c5bbdab62eca918a70dc3ecc2ea9be97e9496c7a7f46d0da7937b3928f292a7`。最新数据仍在设备草稿中，没有自动覆盖云端。

`$value/overviewRefundActivity` 的完整行变更数组，UTF-8 JSON 为 265091 字节，超过前端的 262144 字节目标，准确复现 `A stored record exceeds the batch limit; local backup retained`。其余最大单条约 1.3 KB。云端该根对象的 JSONB 文本为 279301 字节；本次本机对象与之不同，观察变化条目由 738 增为 757。注意：云端 body 字节与本机完整 operation 数组字节的口径不同。

错误发生在 `rowWorkbenchStore.save -> chunkRowChanges` 的预检查，早于创建该保存的 begin 请求。这条错误不是 SQL timeout 或 HTTP 500。

## 最小修复

仅修改 `src/services/workbenchRows.ts` 的分块处理及大小计算：普通块继续 200 项/256 KiB；当单条超过此目标时，仅在其 JSONB 文本计量不超过服务端**已有**的 524288 字节限制时单独发送。考虑 JSONB 空白及指数数字展开，避免用 HTTP JSON 体积代替服务端计量。过大的记录仍在发送前拒绝并保留草稿。

没有更改数据编解码、row diff、RPC、8 MiB 整批上限、账号 revision CAS、幂等回执、原子提交、备份确认、经营结算公式、退款观察算法或任何页面。无需 Supabase SQL/配置操作；仅需批准后重新部署前端。
